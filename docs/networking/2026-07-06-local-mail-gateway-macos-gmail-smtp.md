# Локальный почтовый шлюз на macOS через Gmail SMTP

В UNIX существует очень удачная абстракция: большинство программ не умеют отправлять электронную почту самостоятельно.

Вместо этого они используют стандартный интерфейс `sendmail`, а реализация доставки скрывается за ним.

Благодаря этому приложение может быть написано десятки лет назад и при этом продолжать работать с современной почтовой инфраструктурой. Достаточно заменить реализацию `sendmail`, не изменяя само приложение.

В этой статье я покажу, как настроить macOS так, чтобы программы, поддерживающие `sendmail`-совместимый интерфейс, могли отправлять письма через Gmail SMTP.

## Как работает отправка почты в UNIX

Типичная архитектура выглядит так:

```text
Приложение
    │
    ▼
sendmail interface
    │
    ▼
Mail Transfer Agent
    │
    ▼
SMTP
```

Исторически роль MTA (Mail Transfer Agent) выполняли Sendmail, Postfix или Exim.

Приложение ничего не знает про SMTP, TLS, сертификаты, порты или аутентификацию. Оно просто передает письмо программе `sendmail`, а дальнейшая доставка становится ее задачей.

Именно эта идея позволяет заменить всю почтовую инфраструктуру без изменения прикладного кода.

## Почему я отказался от Postfix

На macOS уже установлен Postfix.

Первоначально я попытался использовать его как SMTP Relay для Gmail.

Удалось:

- настроить STARTTLS;
- проверить SMTP-сеанс через `openssl s_client`;
- вручную выполнить SMTP AUTH LOGIN;
- убедиться, что Google App Password работает.

Однако сама отправка через Postfix заканчивалась ошибкой:

```text
SASL authentication failed; cannot authenticate to server
```

Отладка показала, что проблема находится внутри системной реализации Cyrus SASL, поставляемой вместе с macOS.

Вместо борьбы с системной конфигурацией я выбрал значительно более простое решение.

## Используем msmtp

`msmtp` — небольшой SMTP-клиент, полностью совместимый с интерфейсом `sendmail`.

Установка:

```sh
$ brew install msmtp
```

Конфигурация `~/.msmtprc`:

```text
defaults
auth on
tls on
tls_starttls on
account gmail
host smtp.gmail.com
port 587
from your.name@gmail.com
user your.name@gmail.com
passwordeval security find-generic-password -a oleg.sklyarov@gmail.com -s gmail-smtp -w
account default : gmail
logfile ~/.msmtp.log
```

Добавляем Google App Password в Keychain:

```sh
$ security add-generic-password \
    -a your.name@gmail.com \
    -s gmail-smtp \
    -w
```

Права доступа:

```sh
$ chmod 600 ~/.msmtprc
```

Проверяем соединение:
```sh
$ msmtp --serverinfo
```

Если вывод содержит информацию о TLS и поддерживаемых механизмах AUTH, соединение настроено правильно.

Можно сразу проверить отправку письма:

```sh
$ printf 'To: user@example.com\nSubject: Test\n\nHello\n' | msmtp -t
```

Gmail может переписать или отклонить поле From, если оно не соответствует учетной записи или настроенному alias.

## Интеграция с GNU Mail

Устанавливаем GNU Mailutils:

```sh
$ brew install mailutils
```

Создаем `~/.mailrc`:

```text
set sendmail="/opt/homebrew/bin/msmtp -t"
set from="your.name@gmail.com"
```

На Apple Silicon Homebrew обычно устанавливает программы в /opt/homebrew, а на Intel Mac — в /usr/local.

Путь лучше проверить:
```sh
$ command -v msmtp
$ command -v mail
```

Теперь обычная команда:

```sh
$ echo "Hello!" | mail -s "Test" user@example.com
```

автоматически использует Gmail SMTP.

## Интеграция с PHP

PHP использует программу `sendmail`, путь к которой задается параметром:

```text
sendmail_path="/opt/homebrew/bin/msmtp -t"
```

Найти используемый `php.ini` можно так:
```sh
$ php --ini
```

После изменения конфигурации PHP-FPM или Apache потребуется перезапустить соответствующий сервис.

После этого достаточно обычного вызова:

```php
mail(
    'user@example.com',
    'Test',
    'Hello from PHP'
);
```

Никаких SMTP-библиотек, OAuth или TLS в приложении не требуется.

## Что оказалось неожиданным

Я ожидал, что после настройки `mail` автоматически заработает и `cron`.

Но этого не произошло.

## Первый сюрприз

Встроенный механизм `MAILTO` в `cron` использует системный `/usr/sbin/sendmail`, а не GNU Mail.

На macOS это означает использование Postfix.

В результате Postfix пытался самостоятельно доставить письмо напрямую на MX-сервер Gmail как полноценный почтовый сервер.

Gmail отклонял такие письма, поскольку локальный домен mb-air-15.local не имеет корректных SPF и DKIM записей.

Получалась архитектура:

```text
cron
    │
    ▼
Postfix
    │
    ▼
MX Gmail
```

Хотя ожидалось:

```text
cron
    │
    ▼
msmtp
    │
AUTH
    ▼
smtp.gmail.com
```

Вместо использования MAILTO я стал явно вызывать GNU Mail:

```cron
0-58/2 * * * * \
echo "Cron is working" \
| /opt/homebrew/opt/mailutils/bin/mail \
    -s "Cron stdout test" \
    user@example.com
```

Это полностью обходило Postfix.

## Второй сюрприз

Но письма все равно не отправлялись.

После диагностики выяснилось, что проблема уже не связана ни с Postfix, ни с GNU Mail.

Причиной оказался Keychain.

На этом этапе `~/.msmtprc` все еще использовал:

```sh
$ passwordeval security find-generic-password \
    -a your.name@gmail.com \
    -s gmail-smtp \
    -w
```

Из терминала такая конфигурация работала корректно.

Однако `cron` запускает процессы вне пользовательской GUI-сессии macOS и не имеет доступа к пользовательскому Keychain.

В результате команда security find-generic-password завершалась ошибкой, а msmtp не мог получить пароль приложения.

Пришлось заменить:
```text
passwordeval ...
```
на
```text
password <Google App Password>
```
После этого отправка из `cron` начала работать.

Файл `~/.msmtprc` при этом должен иметь права:

```sh
$ chmod 600 ~/.msmtprc
```

## Итоговая архитектура

В результате получилась следующая схема:

```text
PHP mail()
GNU mail
Shell scripts
cron
        │
        ▼
msmtp
        │
SMTP + STARTTLS + AUTH
        │
        ▼
smtp.gmail.com
```

Все приложения используют единый SMTP-шлюз.

## Что удалось понять

Главный результат этого исследования оказался не в том, чтобы просто отправить письмо через Gmail.

Гораздо интереснее было разобраться, как устроена почтовая подсистема UNIX.

Удалось на практике увидеть разницу между двумя принципиально разными подходами.

### Mail Transfer Agent

```text
Программа
    │
    ▼
Postfix
    │
    ▼
Интернет
```

Postfix самостоятельно доставляет письмо как полноценный почтовый сервер.

Поэтому именно он отвечает за SPF, DKIM, очередь сообщений, повторные попытки доставки и взаимодействие с другими почтовыми серверами.

### SMTP Relay

```text
Программа
    │
    ▼
msmtp
    │
AUTH
    ▼
smtp.gmail.com
```

Здесь компьютер является обычным SMTP-клиентом и передает письмо уже авторизованному серверу Gmail.

Для рабочих станций, ноутбуков, CLI-утилит и большинства небольших приложений этот вариант значительно проще.

## Заключение

После настройки локального SMTP-шлюза через msmtp программы, которым можно указать `sendmail`-совместимую команду, могут отправлять письма без знания SMTP-протокола.

Самым интересным результатом оказалось не то, что письма начали отправляться через Gmail.

Гораздо важнее было увидеть, насколько удачно спроектирована почтовая подсистема UNIX. Приложения десятилетиями используют один и тот же интерфейс `sendmail`, а реализацию доставки можно менять независимо от них.

Именно благодаря этой архитектуре старые CLI-программы, современные PHP-приложения и собственные shell-скрипты могут использовать одну и ту же инфраструктуру отправки почты без каких-либо изменений в своем коде.
