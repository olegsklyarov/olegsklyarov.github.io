# Настраиваем локальный почтовый шлюз на macOS через Gmail SMTP

В UNIX существует очень удачная абстракция: большинство программ не умеют отправлять почту самостоятельно.

Вместо этого они используют стандартный интерфейс `sendmail`, а реализация доставки скрывается за ним.

Это позволяет заменить почтовую систему, не изменяя прикладной код.

В этой статье я покажу, как настроить macOS так, чтобы программы, поддерживающие `sendmail`-совместимый интерфейс, могли отправлять письма через Gmail SMTP.

## Как работает отправка почты в UNIX

Типичная архитектура выглядит так:

```text
Приложение
    │
    ▼
sendmail interface
    │
    ▼
Mail Transfer Agent
    │
    ▼
SMTP
```

Исторически роль MTA выполняли Sendmail, Postfix или Exim.

Приложение ничего не знает про SMTP, TLS, порты, сертификаты или аутентификацию. Оно просто передает письмо программе `sendmail`.

## Почему я отказался от Postfix

На macOS уже установлен Postfix.

Первоначально я попытался использовать его как SMTP Relay для Gmail.

Удалось:

- настроить STARTTLS;
- проверить SMTP-сеанс через `openssl s_client`;
- вручную выполнить SMTP AUTH LOGIN;
- убедиться, что App Password Google работает.

Однако сама отправка через Postfix заканчивалась ошибкой:

```text
SASL authentication failed; cannot authenticate to server
```

Отладка показала, что проблема находится внутри системной реализации Cyrus SASL, поставляемой вместе с macOS.

Вместо борьбы с системной конфигурацией я выбрал значительно более простое решение.

## Используем msmtp

`msmtp` — небольшой SMTP-клиент, полностью совместимый с интерфейсом `sendmail`.

Установка:

```sh
brew install msmtp
```

Конфигурация `~/.msmtprc`:

```text
defaults
auth on
tls on
tls_starttls on
account gmail
host smtp.gmail.com
port 587
from your.name@gmail.com
user your.name@gmail.com
passwordeval security find-generic-password -a your.name@gmail.com -s gmail-smtp -w
account default : gmail
logfile ~/.msmtp.log
```

Изначально я использовал вариант с Keychain, чтобы не хранить пароль приложения в `~/.msmtprc` в открытом виде.

Пароль приложения добавляется так:

```sh
security add-generic-password \
    -a your.name@gmail.com \
    -s gmail-smtp \
    -w
```

После этого `msmtp` читает пароль через `passwordeval`:

```text
passwordeval security find-generic-password -a your.name@gmail.com -s gmail-smtp -w
```

Из терминала такой вариант работает корректно.

Права доступа:

```sh
chmod 600 ~/.msmtprc
```

Проверка:

```sh
msmtp --serverinfo
```

Если вывод содержит информацию о TLS и поддерживаемых механизмах AUTH, соединение настроено правильно.

Можно сразу проверить реальную отправку без `mail`:

```sh
printf 'To: user@example.com\nSubject: Test\n\nHello\n' | msmtp -t
```

Gmail может переписать или отклонить поле `From`, если адрес не совпадает с аккаунтом или настроенным alias в Gmail.

### Безопасность пароля

Если пароль хранится в Keychain, в `~/.msmtprc` остается только команда `passwordeval`.

Но для запуска из `cron` ниже пришлось вернуться к plaintext app password в `~/.msmtprc`.

Для локальной машины это может быть приемлемым компромиссом, но важно соблюдать несколько правил:

- использовать только отдельный Google App Password, а не основной пароль аккаунта;
- держать права `~/.msmtprc` равными `600`;
- не класть этот файл в Git, dotfiles-репозиторий или обычные бэкапы;
- при подозрении на утечку сразу отозвать App Password в настройках Google.

Для production-сценариев лучше использовать отдельный сервисный почтовый ящик и нормальное хранилище секретов.

## Интеграция с GNU Mail

Устанавливаем GNU Mailutils:

```sh
brew install mailutils
```

Создаем `~/.mailrc`:

```text
set sendmail="/opt/homebrew/bin/msmtp -t"
set from="your.name@gmail.com"
```

На Apple Silicon Homebrew обычно ставит пакеты в `/opt/homebrew`, а на Intel Mac — в `/usr/local`.

Перед тем как копировать путь в конфигурацию, лучше проверить его:

```sh
command -v msmtp
command -v mail
```

Теперь обычная команда:

```sh
echo "Hello!" | mail -s "Test" user@example.com
```

автоматически использует Gmail SMTP.

## PHP можно подключить через sendmail_path

PHP использует программу `sendmail`, путь к которой задается параметром:

```ini
sendmail_path="/opt/homebrew/bin/msmtp -t"
```

Где именно менять этот параметр, зависит от способа запуска PHP.

Для CLI можно найти активный `php.ini` так:

```sh
php --ini
```

Если PHP работает через PHP-FPM или Apache, после изменения конфигурации нужно перезапустить соответствующий сервис.

После этого достаточно обычного вызова:

```php
mail(
    'user@example.com',
    'Test',
    'Hello from PHP'
);
```

Никаких SMTP-библиотек, OAuth или TLS в приложении не требуется.

## Что оказалось неожиданным

Я ожидал, что после настройки `mail` автоматически заработает и `cron`.

Но этого не произошло.

Причина оказалась очень интересной.

## Первый сюрприз

`cron` не использует программу `mail`.

Он вызывает системный `/usr/sbin/sendmail`, который принадлежит Postfix.

Из-за этого письма отправлялись напрямую на MX-сервер Gmail и отклонялись:

```text
550 5.7.26
SPF did not pass
DKIM did not pass
```

То есть Postfix пытался работать как полноценный почтовый сервер Интернета.

## Второй сюрприз

Я отказался от встроенного механизма `MAILTO` и стал явно вызывать GNU Mail:

```cron
0-58/2 * * * * \
echo "Cron is working" \
| /opt/homebrew/opt/mailutils/bin/mail \
    -s "Cron stdout test" \
    user@example.com
```

Но письма все равно не приходили.

Тут выяснилось, что проблема уже не в Postfix и не в GNU Mail, а в способе получения пароля для `msmtp`.

На этом этапе `~/.msmtprc` все еще использовал Keychain:

```text
passwordeval security find-generic-password -a oleg.sklyarov@gmail.com -s gmail-smtp -w
```

Из терминала это работало, потому что команда выполнялась внутри пользовательской GUI-сессии macOS и могла достать пароль из Keychain.

Но `cron` запускает задачи в другом окружении. В нем нет нормального доступа к пользовательской GUI-сессии, поэтому `security find-generic-password` не смог получить пароль из Keychain.

В итоге пришлось заменить `passwordeval` на обычный plaintext app password:

```text
password <Google App Password>
```

Это менее элегантно, зато стабильно работает из `cron`. Чтобы ограничить риск, файл `~/.msmtprc` должен быть доступен только владельцу:

```sh
chmod 600 ~/.msmtprc
```

После этой замены отправка заработала.

## Итоговая архитектура

В результате получилась следующая схема:

```text
PHP mail()
GNU mail
Shell scripts
cron
        │
        ▼
msmtp
        │
SMTP + STARTTLS + AUTH
        │
        ▼
smtp.gmail.com
```

В этой схеме единый SMTP-шлюз используют программы, которым можно явно указать `msmtp -t` как `sendmail`-совместимую команду.

## Что удалось понять

Главный результат этого исследования оказался не в том, чтобы «настроить отправку почты».

Гораздо интереснее оказалось разобраться, как устроена почтовая подсистема UNIX.

Удалось на практике увидеть разницу между двумя принципиально разными подходами.

### Mail Transfer Agent

```text
Программа
    │
    ▼
Postfix
    │
    ▼
Интернет
```

Postfix самостоятельно доставляет письмо как полноценный почтовый сервер.

Именно поэтому требуются SPF, DKIM и другие механизмы аутентификации домена.

### SMTP Relay

```text
Программа
    │
    ▼
msmtp
    │
AUTH
    ▼
smtp.gmail.com
```

Здесь компьютер становится обычным SMTP-клиентом и передает письмо уже авторизованному серверу Gmail.

Для рабочих станций, ноутбуков и большинства CLI-инструментов второй вариант значительно проще и надежнее.

## Заключение

После настройки локального SMTP-шлюза через `msmtp` программы, которым можно указать `sendmail`-совместимую команду, могут отправлять письма без знания SMTP-протокола.

Это полностью соответствует классической UNIX-философии: приложение формирует письмо, а доставка делегируется отдельному специализированному инструменту.

В результате один раз настраивается инфраструктура, а приложениям не нужно встраивать собственный SMTP-клиент, TLS-настройки и авторизацию.
